# PBX and contact center feature coverage

Requested scope recorded from the 29 supplied screenshots on 30 October 2026. The screenshots are feature references, not operational instructions or authorization to change the displayed PBX host. Menu visibility identifies requested capabilities; it does not establish the behavior, API availability or licensing of those capabilities.

The same capability set was later compared item by item against the vendor's published `VITALPBX Full Features List` (February 2025) in `docs/VITALPBX_PARITY_REVIEW.md`.

GWO SEVO can be extended toward equivalent capabilities. The current application implements the foundation and domain configuration; it does not yet implement the live PBX functions shown in these references. A feature is complete only when its server behavior, permissions, audit trail, interface and relevant integration tests work together.

## Portal navigation and search coverage

The committed catalogue in `resources/navigation.json` matches the supplied menu specification: six administration sections, 17 administration menus and 237 entries, plus nine Supervisor menus with 35 entries and ten Agent menus with 36 entries. `tests/Feature/NavigationTest.php` pins the administration menu titles, their section mapping and per-section counts so a future edit cannot silently drop a requested menu.

Visibility is computed per account. Menu groups can be disabled with `DISABLED_MODULES`; direct API access to a disabled implemented resource returns 404. Entries without an implementation render a clearly labelled planned page instead of a dead link, so planned scope stays visible without implying completion. Working entries link to configuration, security or Horizon screens that already exist.

The directory is an accordion. The group that owns the page in use stays expanded and any other group collapses when it is opened, so the sidebar never shows two expanded menus at once. A module that is reachable from more than one menu keeps the group the operator is already working in; a deep link or a record jump opens the owning group. While a search term is present every matching group expands so results are not hidden, and `Collapse menu` clears both the expansion and the search. `tests/browser/portal.spec.ts` asserts the `aria-expanded` state of the group toggles.

Administration search covers both menu titles and implemented records. `/admin-api/search` queries sites, departments, teams, skills, extensions, business hours, routing profiles, agents, queues and tenant accounts, capped at 20 results. It reuses `Access::scope` for tenant and site isolation, requires `contact-center.view`, skips records whose module is disabled or whose view permission is absent, and returns links into the matching administration module. The endpoint is a jump list for configuration records; it is not full-text search across calls, recordings, tickets or CRM data, which arrive with those later-phase features.

## Architecture decision required

Two materially different implementations are possible:

1. Integrate the existing VitalPBX installation. Inventory its supported APIs and events with read-only access first. GWO SEVO becomes an administration/contact-center interface over that installation. Confirm one configuration authority per resource and avoid edits that bypass its provisioning lifecycle. Features without a supported API may require a separately managed integration or remain unavailable through the portal.
2. Manage a separate Asterisk server. Laravel owns business configuration and a dedicated gateway applies validated configuration and call commands to Asterisk. This follows the supplied implementation guide but requires implementing provisioning and PBX administration capabilities that an existing PBX product already supplies.

The existing screenshots, hostnames and IP addresses are not connection credentials. No live PBX, network, firewall, server or CRM changes are included in this inventory.

## Delivery sequence and acceptance gates

| Milestone                             | Scope                                                                                                                                 | Acceptance gate                                                                                                                   |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 1 Foundation and configuration        | Existing Phases 1–2 plus expanded grouped navigation, user profiles, audit filters and extension bulk operations                      | Validated configuration persists with tenant/site isolation, explicit permissions, audit records and actionable validation errors |
| 2 Telephony adapter and simulator     | Provider contract, commands, call/queue/agent events, interaction records, agent console and supervisor state                         | Simulated inbound call enters a queue, reaches an agent, is answered/transferred/completed and produces consistent history        |
| 3 Routing and media configuration     | Trunks/routes, ring groups, class of service, IVR, time conditions, announcements, prompts, voicemail configuration and feature codes | Configuration can be validated, simulated, versioned and rolled back; no false claim of live provisioning                         |
| 4 Reporting and operations visibility | CDR/call legs, queue/IVR/callback reports, registration/call dashboard and service metrics                                            | Seeded and simulated events reconcile with defined report calculations; disconnected and stale sources are visible                |
| 5 Live PBX integration                | Selected PBX gateway, WebRTC, inbound/outbound calls, transfer, recording and configuration deployment                                | End-to-end call/media tests pass against the selected engine and SIP provider, including failure and rollback behavior            |
| 6 Advanced PBX and host operations    | Hot desking, conferencing, paging, parking, directories, callback workflows, host management, backups and restore                     | Per-feature integration tests verify the actual PBX or host behavior; a successful form submission alone does not pass            |
| 7 CRM and AI                          | CRM sync/journaling, voice connectors, AI assistants/agents, tools, handoff and reporting                                             | Observable integrations handle retries, deduplication, authorization, latency, failure and human fallback                         |

This sequence covers the visible menu-level scope. Detailed configuration fields, protocols, provider support, retention rules, KPI definitions and emergency-call requirements still need acceptance criteria because screenshots of menus do not specify those behaviors. A menu entry or placeholder page is not feature completion.
