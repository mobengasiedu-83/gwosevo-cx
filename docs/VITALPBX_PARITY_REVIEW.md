# VitalPBX feature parity review

Reviewed 31 October 2026 against `VITALPBX-FULL-FEATURES-LIST-FEBRUARY-2025.pdf` (8 pages, 16 feature sections, 267 listed items). The review maps every listed item to what this repository actually contains: database columns, validation rules, API routes, Vue screens, permissions and tests. It is a gap analysis, not a plan to clone another product, and it does not claim that a configured field produces telephony behaviour.

## Method

1. Extracted the PDF text and grouped it into its 16 published sections (Call Features, Call Center, Voice Mail, Economy, Modules, Administration, Security, Video Conference, Settings, Unified Communications, User Portal, Telephony Interfaces, Signaling Protocols, Codecs, Core Add-Ons, Extended Features).
2. Mapped each item to the committed catalogue `resources/navigation.json` (17 administration menus, 238 entries) to record whether an administration entry exists.
3. Mapped each item to the implementation: `app/Models`, `database/migrations`, `app/Http/Controllers/ContactCenterController.php`, `app/Services/{Navigation,Access,Roles,UnifiedSearch}.php`, `routes/web.php`, `resources/js/pages/Admin/{Index,Extensions}.vue` and `resources/js/schema.ts`.
4. Recorded the status that the code supports. A configuration field that no gateway consumes is never reported as a working call feature.

## Status vocabulary

| Status             | Meaning                                                                                                                       |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| Implemented        | Persisted, validated, permission-checked, audited and covered by a test, and it performs the function it names.               |
| Configuration only | The data model, validation and screens exist, but nothing executes the PBX behaviour yet. The item is stored, not performed.  |
| Menu only          | An administration entry exists and renders the labelled planned page; no model or endpoint backs it.                          |
| Missing            | No catalogue entry and no model.                                                                                              |
| Not applicable     | Depends on host hardware, another product's licensing or the deployment, so it cannot be delivered by this application alone. |

The 267 items include repeats across sections: VitalPBX lists voicemail-to-email twice under Call Features and product-wide items again under Modules, Unified Communications and Administration. Counts follow the published bullets, so a feature can appear as configuration only in one section and as a planned page in another.

Nothing in this repository places a call, registers a SIP endpoint, stores a recording or reads CDR. The delivered scope is the control plane: tenancy, site scoping, permissions, audit, a directory that mirrors the requested menu specification, and configuration records for sites, departments, teams, skills, extensions, business hours, routing profiles, agents and queues. 25 of the 238 administration entries are wired to real endpoints (`extensions`, `routing-profiles`, `business-hours`, `queues`, `skills`, `agents`, `teams`, `accounts`, `roles`, `audits`, `settings`, `departments`, `sites`, `@security`, `@horizon`); the remaining 213 are planned pages.

## Findings

1. **The catalogue is broader than the implementation, and its shape comes from screenshots rather than from user tasks.** 238 entries against 25 wired ones means 89% of the administration menu resolves to a labelled "planned" page. That is honest by design (`Navigation::catalogue` sets `status`), but it sets a false expectation when a prospective customer browses it. Keep the placeholders and surface a coverage indicator per group.
2. **Where depth exists, it is well engineered.** Extensions carry more than 60 validated columns, three encrypted secrets, per-tenant uniqueness and a dedicated tabbed editor; queues model member priority and required skill proficiency; permissions are per resource and per verb with site scoping; every write is audited; 27 PHPUnit tests and 2 Playwright tests cover the flows. The problem is breadth, not craft.
3. **Three everyday telephony controls have no entry at all.** Call Forward, DND and BLF are absent from a 238-entry catalogue while `Call Transfer Rules` is present. Correct the catalogue before adding screens.
4. **DIDs, pickup groups and call groups are strings on an extension, not objects.** `pickup_group` and `call_group` are comma-separated digit lists; `incoming_routes` is a JSON array of DID/description pairs; there is no trunk. These need first-class tables before a provisioning adapter can consume them.
5. **`routing_profiles` is doing three unrelated jobs**: queue strategy, business-hours binding and overflow. That is a reasonable MVP, but trunk, route and IVR work must not be bolted onto it.
6. **Codec handling accepts anything.** `extensions.codecs` is free text matching `^[A-Za-z0-9,._-]+$`. A validated multi-select against the chosen engine's codec list is a small, worthwhile change.
7. **Security controls are accurate but narrower than the VitalPBX list.** Real: roles, site scoping, MFA, session revocation, audit and a 12-character mixed-case account policy. Absent: PINs, phone lock, weak-credential reporting, host firewall, fail2ban and VPN. Do not claim the absent ones before a host agent exists.
8. **The self-service portal is the highest-leverage next feature.** Seven User Portal items (forward, DND, presence, call history, voicemail, greetings, visual voicemail) share one call-control contract, so one adapter plus one screen moves all seven.
9. **Hardware and licensing parity is out of reach by design.** DAHDI, BRI/E1/T1/R2, FXS/FXO, ISDN, GSM, G.729 licensing and hypervisor support are properties of a PBX distribution, not of a Laravel administration layer. Record them as engine capabilities in any comparison table.
10. **`docs/FEATURE_COVERAGE.md` now understates extension depth.** It was written before the tabbed editor landed; its Extensions row should mention follow-me lists, DID rows, codec/transport/DTMF device fields and encrypted secrets.
